### Функциональные требования

| №  | Действующие лица или системы | Use Case | Описание |
| :-: | :- | :- | :- |
| 1 | Клиент (новый) / Сайт / Система кол-центра | Подача заявки на депозит с сайта | Новый клиент выбирает депозит на сайте, заполняет ФИО и телефон, данные шифруются и передаются в систему кол-центра, менеджер связывается с клиентом |
| 2 | Клиент (действующий) / Интернет-банк / АБС | Подача заявки на депозит в ИБ | Клиент авторизуется в ИБ, видит список депозитов и персональные ставки, выбирает счёт и сумму, подтверждает СМС-кодом, заявка передаётся в АБС для обработки бэк-офисом |
| 3 | Менеджер кол-центра / Система кол-центра | Обработка заявки с сайта | Менеджер видит заявку в системе, может предложить клиенту стандартные или особые условия, фиксирует договорённости |
| 4 | Менеджер бэк-офиса депозитов / АБС | Подтверждение условий депозита | Менеджер в АБС проверяет ставку (по XLS-данным или новой функциональности хранения ставок в АБС), подтверждает заявку, инициирует открытие депозита |
| 5 | СМС-шлюз / Телеком-оператор | Оповещение клиента | После подтверждения условий и открытия депозита клиент получает СМС об успешном оформлении |

### Нефункциональные требования

| №  | Требование |
| :-: | :- |
| 1 | Доступность сервисов (сайт, ИБ, интеграции) — не ниже 99,9%, режим 24/7 |
| 2 | Отказоустойчивость при сбоях ЦОД (переключение на резервный ЦОД без долгих простоев) |
| 3 | Шифрование данных при передаче между клиентом и системами, а также между системами банка (HTTPS/TLS) |
| 4 | Время отклика интерфейса — в пределах миллисекунд |
| 5 | Горизонтальное масштабирование для ИБ и веб-сервисов; минимизация нагрузки на БД АБС |
| 6 | Использование технологий, по которым уже есть экспертиза (MS SQL, Oracle, Java, .NET) |
| 7 | Возможность расширения архитектуры на другие продукты (например, кредиты) |
| 8 | Соответствие требованиям по обработке персональных данных |

### Решение

Диаграмма контекста (C4 Level 1)  
Показывает участников и основные системы:  
- Каналы: сайт, интернет-банк  
- Системы: АБС, система кол-центра, СМС-шлюз, телеком-оператор  
- Пользователи: клиенты, менеджеры кол-центра, бэк-офис депозитов  

Диаграмма контейнеров (C4 Level 2)  
Детализация ИБ и АБС:  
- В интернет-банке выделен новый модуль «Депозиты» (отдельный контейнер в монолите), интеграция через API-шлюз/промежуточный сервис с АБС  
- В АБС — модуль «Обработка заявок на депозиты» с хранением ставок в Oracle (общедоступно для бэк-офиса депозитов и кредитов)  
- Интеграция сайта с системой кол-центра — через защищённый REST API  
- Оповещение клиентов — через СМС-шлюз, интегрированный с АБС  
- Предусмотрена возможность кэширования и промежуточного хранения данных ставок для снижения нагрузки на АБС  

Логика выбора технологий:  
- Сохранение совместимости с текущим стеком (MS SQL, Oracle, Java, .NET)  
- Минимизация доработок в ядре интернет-банка и существующих системах  
- Избежание прямой интеграции ИБ с АБС для снижения нагрузки и повышения отказоустойчивости  
- Возможность горизонтального масштабирования фронт- и мидл-уровня  

---

### Альтернативы

1. Прямая интеграция ИБ с API АБС  
   Плюсы: упрощает архитектуру  
   Минусы: высокая нагрузка на БД АБС, риски доступности  

2. Хранение ставок в отдельной БД вне АБС  
   Плюсы: снижение нагрузки на АБС  
   Минусы: появление дублирования данных и необходимости синхронизации  

---

Недостатки, ограничения, риски  

- Ограниченная масштабируемость АБС (только вертикальная) — риск при росте числа заявок  
- Текущая версия интернет-банка несовместима с Kafka, что ограничивает выбор очередей сообщений  
- При хранении ставок в XLS-файлах высок риск ошибок и задержек; потребуется миграция данных  
- Возможные доработки в системе кол-центра и АБС могут потребовать участия сторонних подрядчиков
